인자 `$ARGUMENTS`에서 첫 번째 단어를 타입(TYPE), 두 번째 단어를 이슈번호(ISSUE_NO)로 해석해.

반드시 아래 규칙 파일을 우선 참고해:
- `.claude/rules/commit.md`
- `.claude/rules/response-exception.md`

작업 순서:
1. 타입이 `feat/fix/chore/docs/refactor` 외이거나 이슈번호가 없으면 실행 전에 알려주고 중단한다.
2. `gh issue view {ISSUE_NO}` 로 이슈 상세 정보 조회
3. 이슈 제목에서 브랜치 슬러그 생성
   - `[✨ Feat]` 형태의 이모티콘/접두사 제거
   - 한국어는 의미를 유지하며 영어로 번역
   - 영어 소문자 + 하이픈만 사용 (공백 → 하이픈, 특수문자/이모티콘 → 제거)
   - 예: `[✨ Feat] 로그인 API 구현` → `login-api`
4. 브랜치명 확정: `{TYPE}/{ISSUE_NO}-{슬러그}`
5. `git checkout -b {브랜치명}` 으로 브랜치 생성
   - 이미 존재하면 `git checkout {브랜치명}` 으로 전환 후 이미 존재함을 명시
6. 이슈 내용을 분석해 **실패 시나리오를 먼저 도출**하고, 그 다음 구현 계획을 작성한다 — 코드는 구현하지 않는다

출력 형식:

## 브랜치
- 생성(또는 전환)한 브랜치명

## 이슈 요약
- 이슈 제목과 핵심 목표 한 줄 요약

## 실패 시나리오 (구현 전 먼저 정의)

구현 전에 발생 가능한 모든 실패 케이스를 아래 카테고리별로 열거한다.
이 목록이 구현 계획과 ErrorCode 설계의 기준이 된다.

### 인증/인가
- 누가 이 API를 호출할 수 있는가? 인증 없이 접근 시 어떻게 되는가?
- 본인 리소스가 아닌 타인 리소스에 접근하면?
- STOMP 핸들러라면: `@AuthenticationPrincipal` 대신 `Authentication` 파라미터 사용 여부 확인

### 입력값 검증
- null, 빈값, 범위 초과, 음수, 중복 등 잘못된 입력이 들어오면?

### 비즈니스 규칙 위반
- 존재하지 않는 리소스를 참조하면?
- 상태 전이 규칙을 어기면? (예: 이미 삭제된 항목 수정)
- 중복 생성, 자기 자신 대상 작업 등 도메인 규칙 위반 시?

### 트랜잭션 경계 밖 사이드이펙트
- `@Transactional` 메서드 안에서 Redis, 이메일, 외부 API 호출이 있는가?
- TX 롤백 시 사이드이펙트가 복원되지 않는 문제가 생기는가?
- 해결이 필요하면: `@TransactionalEventListener(AFTER_COMMIT)` 패턴 적용 여부 결정

### 동시성/중복 요청
- 동시에 같은 요청이 두 번 들어오면 중복 데이터가 생기는가?
- DB 유니크 제약이 있는가? 없다면 추가해야 하는가?

### 외부 의존성 실패
- DB, Redis, 외부 서비스가 실패하면 어떻게 처리하는가?
- 실패 시 무음 무시할 것인가, 예외를 던질 것인가?

### response-exception.md 체크
- [ ] Controller 반환 타입이 `ResponseEntity<ApiResponse<T>>` 또는 `ResponseEntity<Void>`인가
- [ ] Service/Domain이 `ApiResponse`나 `ErrorResponse`를 반환하지 않는가
- [ ] 비즈니스 예외가 `CustomException`으로 던져지는가
- [ ] 새 `ErrorCode` 추가 시 접두사가 도메인 기준에 맞는가
- [ ] 새 `ErrorCode` 번호가 기존과 중복되지 않는가
- [ ] TX 경계 밖 사이드이펙트가 있다면 AFTER_COMMIT 처리를 계획했는가

주의:
- 이슈 내용이 부족하면 추측으로 채우지 마. 정보가 없는 항목은 "이슈에 명시되지 않음"으로 표기해.
- 실패 시나리오가 명확하지 않으면 구현 계획을 확정하지 말고 사용자에게 먼저 확인한다.
- 계획 출력 후 코드를 바로 구현하지 마. 사용자 확인 후 진행 여부를 결정한다.
